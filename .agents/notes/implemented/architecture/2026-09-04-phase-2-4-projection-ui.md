# Agent Note: Phase 2.4 — Projection unit + Web UI project list

Status: implemented

## Problem

Phase 2 prompt §4 reserves Phase 2.4 for "verify the 1.5.4 projection unit end-to-end and add the live-session-count badge to the projects pane". The 1.5.4 work ([Agent Note](../../implemented/architecture/2026-08-31-projection-cache-integration.md)) wired a `project` projection unit into `ctx.sessionProjections` and taught the persisted projection cache to checkpoint its state, but no consumer of the unit existed yet. Phase 1.5.3 ([Agent Note](../../implemented/architecture/2026-08-30-app-builder-shell-on-upstream-web.md)) built the projects pane as a snapshot-polling client whose `AppBuilderSnapshot` shape covers `projects` + `devServers` but no live-session signal. Two gaps gaps are open at the start of 2.4:

1. **No host-side consumer of the 1.5.4 projection unit.** The unit is registered and exercised by its own test suite, but nothing in the App Builder host reads its state. `getUsage`'s projectId-only path (Phase 2.3) returns a typed `not-implemented` failure precisely because the aggregation belongs to a unit owned by the projection registry.
2. **No live-session signal in the projects pane.** A user opening the App Builder shell sees the project list but but a no indication of which projects have active sessions, which makes the per-project session count (`0 / 1 / many`) a routine "is this scaffold in use?" question that the UI cannot answer.

The pre-existing snapshot-bridge test `packages/app-builder/snapshot-bridge/tests/loader-composition-test.ts` mounts the project plugin without `sessionProjections`, which became an `inject` dependency after 1.5.4. The test never reached the bridge code path so the failure stayed latent; `pnpm run test` on the base (before any 2.4 commit) reproduces the failure identically.

## Decision

Wire a per-project live-session-count signal from the 1.5.4 projection unit into the snapshot-bridge's published `AppBuilderSnapshot`, then surface it as a per-row badge in the projects pane. The change is scoped to the snapshot-bridge + the projects pane client + a host-bridge consumer; no new package is introduced because the consumer view is one JSON field on one existing snapshot, and the projection unit is the canonical owner of `session → project` resolution.

### Host side

- `AppBuilderSnapshot` gains a new field `sessionCounts: Readonly<Record<string, number>>` keyed by project id. The bridge recomputes the map on every flush by walking `ctx.sessions.list()` once and resolving each session's owning project through the projection cache (preferred: zero I/O, durable value), falling back to the live `ctx.sessionProjections.snapshot(session)` registry walk when the cache is unmounted or the session has no checkpoint row. Sessions whose projection resolves to `null` (no cwd, cwd outside any project) do not contribute to any key.
- The bridge subscribes to `session/created` and `session/disposed` (in addition to the existing `project/created`, `project/deleted`, `app-builder-preview/dev-state`) so the count stays coherent with session lifecycle. The cache-backed read is the fast path; the live walk runs only when the cache is absent.
- `EMPTY_SNAPSHOT` ships `sessionCounts: {}`. Missing / malformed `sessionCounts` in a pre-2.4 host's snapshot degrades to an empty map (forward-compat, see Alternatives #2).
- The bridge publishes `ctx.appBuilderSnapshotBridge` through `ctx.reflect.provide` instead of direct property assignment (pre-existing bug masked by the broken pre-existing test; the original direct-assign throws "cannot set property without provide" under the current cordis reflection contract).

### Client side

- The projects pane `AppBuilderSnapshot` type gains the same field. `normalizeSnapshot()` coerces it: empty map on missing / non-record values, plain-string keys with non-negative finite numeric counts otherwise; non-finite / negative numbers are filtered out so `sessionCounts[project.id]` never returns a corrupt value.
- `ProjectsList` reads `state.snapshot.sessionCounts[project.id]` and renders a small chip-style badge when the count is positive. The badge omits for count === 0 or undefined, matching the host's empty state and keeping the row minimal for projects with no live sessions.
- The locale namespace gains two keys: `sessionCountOne` (`1 session`) and `sessionCountOther` (`{count} sessions`). `Intl.PluralRules('en').select(n)` picks between the two arms; `few` / `many` / `zero` are absent and the formatter falls back to `other`. The Chinese sidecar (`sessionCountOne` = `1 个会话`, `sessionCountOther` = `{count} 个会话`) keeps the bilingual invariant the locale ownership Agent Note requires for client UI copy.
- The render-site consumes the dictionary through the existing `t` helper, applies a `{count}` template substitution, and announces the count to assistive tech (`aria-label`).
- The shell renderer is unchanged; it threads the `selectedProjectId` into the projects slot owner prop exactly as before. The new badge lives entirely inside the projects pane.

### Test surface

- `packages/app-builder/snapshot-bridge/tests/snapshot-session-counts.spec.ts` (new) drives the bridge through real Loader composition: it mounts the session store, the projection registry, the persisted projection cache, the project plugin, and the bridge itself, then exercises six branches — cache-backed composition with one inside / one outside / one no-cwd / one pre-project session, cache-absent fallback, count decrement on a disposed session, and burst-safety against a burst of `project/created` events.
- `packages/client/ui-app-builder-projects/tests/projects-list.client.spec.tsx` (new, `@vitest-environment jsdom`) renders the pane against stubbed props and covers 15 branches: the four status colors, the snapshotUnconfigured + snapshotUnavailable banners, the empty-state hint, the Intl.PluralRules arms (1 / >1 / 0 / missing key / missing field), the per-row selection mirror, and the row click routing through the inject `selectProject` callback.
- `packages/client/ui-app-builder-shell/tests/shell.client.spec.tsx` (new, `@vitest-environment jsdom`) renders the shell against stubbed props and covers 6 branches: the localized header, the projects slot owner-prop handoff, the conversation slot empty owner, the no-project-selected empty state, the preview slot owner-prop handoff when a project is selected, and the `data-app-builder-enabled` attribute the e2e boot check reads.

## Alternatives considered

1. **Publish the session-count map as a separate JSON endpoint instead of a snapshot field**. A separate endpoint would let the browser pane poll at a finer cadence and decouple from the projects-state change rate, but the snapshot-bridge is already the canonical host-to-browser projection for App Builder state, and a parallel endpoint would either duplicate the polling infrastructure or require a new client-side store. The chosen design reuses the existing polling loop so the projects pane never grows a second timer; the count walks O(N sessions) per flush and the flush fires on lifecycle boundaries, so the cadence cost is bounded.
2. **Surface the count through a new Cordis service the BFF reads via `appBuilderApi.listSessionCounts()`**. A BFF method would let the BFF cache the count independently of the snapshot file and would integrate with the `getUsage` projectId-only path that 2.3 deferred. The chosen design publishes the count through the snapshot file because the projects pane is a a polling client with no BFF-Remote reads yet; a BFF method would require either replacing the polling loop (out of scope for 2.4) or running two parallel reads. The 2.5 / 2.6 follow-through can replace the polling loop with a BFF-Remote reader once it lands.
3. **Walk the projection registry directly instead of going through the projection cache first**. The cache-backed path is the zero-I/O, durable-value fast path the 1.5.4 Agent Note reserved for the host's read site; the registry walk is the fallback for the cache-absent deployment (a Phase 2 deployment that mounts the bridge without the projection cache). The chosen design prefers the cache and only falls back when the cache is unmounted or returns `undefined` for the session header.
4. **Render the badge as text only ( no `data-session-count` attribute, no `aria-label`)**. The badge needs to be readable by the testing-library selector (which the 2.4 client spec drives via `querySelector('[data-session-count]')`), and assistive tech needs the count announced in a way that survives the visual presentation. The chosen design carries both the data attribute (test selector + future programmatic read) and the aria-label (screen reader announcement).
5. **Rebase the 2.4 stack on a single commit instead of a stacked PR**. The pre-2.4 PR stack (2.1 deployment → 2.2 tool-policy → 2.3 api-completion) is a native GitHub stacked PR chain; rebasing 2.4 onto `master` would collapse the chain and require every preceding PR to re-review. The chosen design preserves the stacked-PR shape (this PR targets `feat/phase2-2-tool-policy`, the same target 2.3 used); 2.6 will rebase `docs/phase2-record` atop merged 2.5 head once the stack lands.

## Consequences

- **A per-project live-session-count badge ships on the projects pane.** The badge carries the count through `Intl.PluralRules('en')` (one vs. other), the locale dictionary, and the `{count}` template substitution. Zero / undefined / missing-key cases render no badge so the row stays minimal for projects with no live sessions.
- **The snapshot-bridge becomes the read site for the 1.5.4 projection unit.** The bridge's `computeSessionCounts` walk is O(N sessions) per flush and runs on `project/created`, `project/deleted`, `session/created`, `session/disposed`, and `app-builder-preview/dev-state`. The cache-backed read is zero-I/O; the live walk is the cache-absent fallback. Sessions outside any project (no cwd, cwd outside any project root) do not contribute to any key.
- **Pre-existing `ctx.appBuilderSnapshotBridge` provide bug fixed.** The bridge now publishes the accessor through `ctx.reflect.provide('appBuilderSnapshotBridge', …)` instead of direct property assignment. The original direct assign throws "cannot set property without provide" under the current cordis reflection contract; the failure was masked by the broken pre-existing `loader-composition-invariant.spec.ts` test that never reached the bridge code path.
- **Forward-compat with pre-2.4 host snapshots.** The client's `normalizeSnapshot` coerces missing / non-record / malformed `sessionCounts` to `{}` so the pane renders no badge against a pre-2.4 host. Non-finite / negative numbers are filtered out so `sessionCounts[project.id]` never returns a corrupt value.
- **Bilingual invariant preserved.** `sessionCountOne` and `sessionCountOther` ship in both English and Chinese dictionaries; the locale ownership Agent Note ([2026-08-23-locale-owned-client-ui-copy.md](./2026-08-23-locale-owned-client-ui-copy.md)) requires every client UI string to be bilingual, and this PR follows the convention.
- **Three new test files cover the host-side cache walk + the client-side render paths.** The host suite drives real Loader composition (SessionStore + SessionProjectionRegistry + Storage + StorageJson + StorageDomain + SessionProjectionCache + AppBuilderProject + bridge), mounts them through the same `ctx.plugin` path the bundle uses, and asserts the count map against six real composition branches. The two client suites render the components directly through `@testing-library/react` against stubbed props so the renderer stays a pure function of its four prop shares. The pre-existing test surface is untouched.
- **Pre-existing `loader-composition-invariant.spec.ts` failure carried forward to the §9 backlog.** The 2.4 fixes the same bridge code path the broken test was originally written to cover (the bridge's `flush` on `project/created` + the HTTP route serving `{ ts, projects, devServers }`). The test still fails to mount because `@deepseek-ai/dsh-app-builder-project` declares `inject: ['sessionProjections']` after 1.5.4 and the test never mounted `SessionProjectionRegistry`. Fixing the test is out of scope for 2.4 (it requires adding the projection registry to the test's `ctx.plugin` calls); the §9 entry records the carry-forward.
- **Phase 2 sub-phase stack base.** This PR is the fourth code sub-phase atop `docs/phase2-record`, based on `feat/phase2-3-api-completion` (2.3 head `bfba258158`). The stack base is `origin/docs/phase1.5-record` = `26bf01ba4a`; subsequent code sub-phases (2.5 Web UI + EventSource) base on this branch, and the 2.6 closure docs rebase `docs/phase2-record` atop merged 2.5 head.
