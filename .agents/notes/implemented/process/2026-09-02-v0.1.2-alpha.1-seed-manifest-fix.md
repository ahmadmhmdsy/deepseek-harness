# Agent Note: Phase 1.5 post-merge fix-up — web shell static-link transitive deps

Status: implemented

English

A companion to the [merge-upstream-dsh-v0.1.2-alpha.1](2026-08-30-merge-upstream-dsh-v0.1.2-alpha.1.md) note; the original merge shipped two post-merge follow-ups (catalog drift gates, stale `apiproxy/lib/` cleanup). This third follow-up is the one discovered when the boot browser-side failed to materialize `@deepseek-ai/dsh-api-session-controller` after the merged tree went live.

## Problem

The first browser load of `dsh web` against the merged `master` reports:

```
client-modules: require("@deepseek-ai/dsh-client-store") missed the module table
— not a platform seed word, not a materialized module,
and no registered package factory
(a build-time externals drift, or a dynamic dependency that did not arrive)
```

`packages/client/web/src/seed.ts` correctly declares `@deepseek-ai/dsh-client-store` in `PLATFORM_MODULES` and statically imports it as a value namespace, so the runtime module-table seed *should* have the entry. The runtime ladder in `packages/client/modules/src/client/system.ts` first checks `this.seed.has(spec)` against that table; the failure on the first branch proved the seed population is broken, not the runtime logic.

Inspecting the Vite-built shell output (`apps/web/dist/assets/index-*.js`) reveals the cause: the bundled seed-map function emits seven keys — `react`, `react/jsx-runtime`, `react-dom`, `react-dom/client`, `@deepseek-ai/cordis`, `@deepseek-ai/dsh-client-ui-slots`, `@deepseek-ai/dsh-client-ui-primitives` — but **no `@deepseek-ai/dsh-client-store`**. Vite/Rollup tree-shook the namespace import. The only difference between `client/store` (tree-shaken) and `ui-slots` / `ui-primitives` (preserved) is the runtime bare-import chain: `client/store/lib/index.js` re-exports from `zustand/vanilla`, `zustand/middleware`, `zustand/shallow`, and `immer`, while the two `ui-*` libraries bundle everything inline.

`zustand` and `immer` are `packages/client/store`'s declared `dependencies`, so pnpm nests them under `apps/web/node_modules/@deepseek-ai/dsh-client-store/node_modules/{zustand,immer}`. Node.js would resolve them; Vite (and the esbuild prebundler) walks the import graph from the shell's entry and cannot find them through that path, so the entire `ClientStore` module falls out of the seed map.

The merge inadvertently broke the static-link contract by introducing a feature plugin whose client bundle reaches into `client/store` for the snapshot-store engine at runtime, while `client/store` itself has runtime deps that only exist in its own nested `node_modules`.

## Decision

Promote `zustand` and `immer` to direct `devDependencies` of `apps/web` (with versions matching `packages/client/store/package.json`: `zustand: ~4.4.7`, `immer: ^10.1.1`). pnpm hoists them into `apps/web/node_modules/`, so Vite resolves them when bundling the shell. The bundled seed map now emits `@deepseek-ai/dsh-client-store` and the runtime `require` resolves. `pnpm install --filter @deepseek-ai/dsh-web-frontend` + `pnpm --filter @deepseek-ai/dsh-web-frontend run build` + restart `dsh web` is the full fix.

This decision operationalizes the [client-shells-and-dynamic-packages decision](../architecture/2026-08-15-client-shells-and-dynamic-packages.md):

> "The `staticLinked` preset leaves every bare specifier as an external import in `lib/index.js` and emits relative CSS assets beside it. **The Vite host resolves and deduplicates those imports and decides final chunk boundaries.** A static library therefore does not copy the host's bundling policy into its own artifact."

"Resolves and deduplicates" is not automatic — the Vite host needs the bare specifiers to be reachable from its own resolution context. pnpm strict mode keeps workspace packages' transitive deps in their nested `node_modules`, so any staticLinked package whose `lib/index.js` keeps a bare import becomes a hidden build-time prerequisite for the host. The host must declare those deps in its own `devDependencies` to keep the static-link mechanism honest.

This also aligns with the [client-cross-package-value-dependencies decision](2026-08-23-client-cross-package-value-dependencies.md) — runtime values cross package boundaries only via the seed mechanism (PLATFORM_MODULES) or `dsh.client.external` for transport. `client/store` reaches consumers through the seed mechanism, which is exactly the path the merged tree wires up correctly in source; this fix makes the build preserve that wiring all the way through Vite.

## Alternatives considered

**Add `@deepseek-ai/dsh-client-store` to `packages/api/session-controller/package.json` `dsh.client.external`.** The merge explicitly narrowed this escape hatch: `verify-client-packages` rejects every `dsh.client.external` declaration under `packages/client/*`, and the only retained non-`packages/client/*` requests are transport infrastructure (Session Controller → API Gateway, Workspace Controller → API Gateway). Adding `client/store` here would be a feature plugin asking for a feature plugin, which the gate refuses and which the rule forbids. Rejected.

**Convert `dsh-client-store` to a `clientBundle` build (add a `lib/client.js` factory + `dsh.client` declaration).** That moves the package from the static-link channel into the dynamic module-table channel, contradicting the [client-shells-and-dynamic-packages](../architecture/2026-08-15-client-shells-and-dynamic-packages.md) classification that puts `client/store` in the narrow static owner set (`client/store`, `ui-primitives`, browser-safe utility packages). Rejected — would break the architectural role.

**Refactor `packages/api/session-controller/src/client/**` to stop reaching into `client/store` for the runtime store primitives (`notifySubscribers`, `createSnapshotStore`); push them through Cordis service injection.** Architecturally correct (the source of the original `client-modules: require … missed the module table` message was always that the dynamic client bundle required a static-link library directly, not the seed mechanism); but it touches six consumer files and a Cordis service seam that the merged tree does not declare. Out of scope for a hot-fix-up. Rejected for this PR; tracked separately as a follow-up architecture cleanup if the upstream code keeps growing consumer surfaces.

**Pin the build to skip tree-shaking with a no-op side-effect reference in `seed.ts`.** Anti-pattern: hides the real coupling (the host's missing deps) under a runtime-side hack. Rejected.

## Invariants

- Every staticLinked package's `lib/index.js` bare imports resolve from the Vite host's `apps/web` package context. The host declares each such transitive dep as a direct `devDependencies` entry; the version range matches the staticLinked package's own `dependencies` declaration exactly.
- `PLATFORM_MODULES` (in `packages/client/web/src/platform.ts`) and the static-import roster in `packages/client/web/src/seed.ts` continue to satisfy the `Record<PlatformModule, unknown>` `satisfies` pin. A drift between the two lists is a compile error, not a runtime seed miss.
- The bundled seed map under `apps/web/dist/assets/index-*.js` contains every `PLATFORM_MODULES` entry. CI cannot assert this directly today; the manual check is `node -e "…grep @deepseek-ai/dsh-client-store apps/web/dist/assets/index-*.js"` after a `vite build`. Future: a `verify-bundled-seed-map` gate that walks the bundle and compares keys against `PLATFORM_MODULES`.
- `pnpm run verify-client-packages` continues to reject `dsh.client.external` declarations under `packages/client/*` and to reject feature-plugin runtime value requests across package boundaries; this fix does not relax any client-package gate.

## Consequences

- `apps/web/package.json` gains two `devDependencies` entries (`immer`, `zustand`) with versions pinned to `client/store`'s declared ranges. The shell's dependency surface now exposes two libraries it does not directly import; the rationale (`client/store` runtime contract) belongs to this note and to `apps/web/README.md` if one exists. No published package boundary changes; `apps/web` is a build consumer, not a workspace library.
- The fix is a one-line manifest addition plus a rebuild. It does not touch `packages/client/store`, `packages/api/session-controller`, or any other workspace package; the merged tree's source remains untouched.
- Browser boot now loads `dsh-api-session-controller` (and the dependent `workspace-controller`, `settings-controller`, `subagent-model-selection-settings`) without the runtime seed miss. The remaining `pnpm run hygiene` failures on the merged tree (knip, publint, verify-client-packages pre-existing drift on `ui-app-builder-{shell,projects}`, constraints) are unrelated; they were failing before this fix and stay failing until the per-area follow-up sub-phases (1.5.7 catalog generators, 1.5.3 webworker-runtime corpus, 1.5.2 examples relocation) address them.
- The architectural lesson is a build-time corollary of the static-link contract. The [client-shells-and-dynamic-packages](../architecture/2026-08-15-client-shells-and-dynamic-packages.md) note already states the design intent; this note makes the build-time consequence explicit. A future cleanup PR can lift the explicit dep list into a single generated declaration (`scripts/sync-static-link-host-deps.ts` walks every `staticLinkedConfig` output's bare specifiers and writes the host's `devDependencies` block) so adding a new staticLink package cannot silently break the host build again.

## Risks

The two new direct deps are workspace-external `pnpm` packages (`immer`, `zustand`). pnpm will hoist them on next install; a future workspace-tooling change (e.g., moving to `node-linker=hoisted` or removing the `apps/web/devDependencies` section in favour of an explicit lockfile-driven resolver) could re-break the resolution. The risk is mitigated by the planned cleanup script (see Consequences) but until it ships, a manual sanity check after `pnpm install` (`node -e "require.resolve('zustand/vanilla', {paths:['apps/web']})"`) catches regressions early.

The manual seed-map check (see Invariants) is not yet automated. A regression that drops `client/store` from the bundle would re-introduce the original runtime failure; CI would not catch it until a browser smoke surfaces it. Adding the `verify-bundled-seed-map` gate is part of the follow-up.
